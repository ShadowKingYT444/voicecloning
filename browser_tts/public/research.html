Research note · October 2026

Small speech models,
inside the browser.

This reader uses a selected ASMR voice, a quantized Chatterbox Nano conversion, and WebGPU. The target is smooth long-text playback with runtime memory below 500 MiB. That target is not yet verified.

A selected voice state

The reference encoder runs offline. Its four output tensors are saved as a small voice artifact. The browser verifies this artifact and loads it before downloading model weights. The browser does not load the reference encoder.

The selected reference is a generated sample. Its conditioning state does not include the repository's fitted adapter weights. Similarity to the custom voice still needs matched listening and quality checks.

Three graphs during reading

  1. The tokenizer and embedding graph turn each passage into text vectors.
  2. The language model predicts speech tokens and reuses a 24-tensor key/value cache on WebGPU.
  3. The acoustic decoder turns the complete token sequence into a 24 kHz waveform.

The decoder returns a complete passage. The reader starts playback after the first passage is decoded and generates the next passage during playback. It keeps at most two passages queued. Independent passages can change prosody or add pauses.

Download and runtime memory

The three published graph and weight pairs total 374.14 MiB. Tokenizer and configuration files bring the model assets to 377.54 MiB. The earlier four-graph package was approximately 547 MiB with tokenizer files. The reader now uses Blob-backed external weights with ONNX Runtime Web 1.30 JSPI. This avoids the loader's complete external-weight ArrayBuffer path.

Runtime memory also includes activations, caches, WebAssembly, WebGPU buffers, and browser processes. Only direct measurements can establish the memory budget. Model download size is not a runtime measurement.

A streaming comparison

Kyutai Pocket TTS is another small voice-cloning model. Its upstream project reports audio streaming and a 200 ms first chunk on its supported Python path. The project lists community WebAssembly and ONNX Runtime Web ports, but does not officially support browser inference. Those latency claims are not browser measurements. Pocket TTS is a useful follow-up if the Nano passage queue leaves long gaps.

What this test measures

  • Model initialization and estimated time until scheduled playback.
  • Latest passage synthesis duration and total generated audio.
  • Mean real-time factor for the current reading session.
  • Scheduled playback gaps. Voice quality requires direct listening.

The page does not measure browser-process RSS or GPU memory. Those require process-level measurements. Completed passages are saved to browser storage. Chrome can stream the WAV export to a local file. Playback and export use the same short edge fades. This reduces clicks. It cannot remove pauses or prosody changes between independently generated passages. The reported performance from this machine will not predict other devices. The original browser brief’s latency values are native-runtime results or targets, not browser measurements.
